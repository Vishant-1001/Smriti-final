# SCOPE v2.1 experiment protocol (frozen before the definitive run)

**Status: experimental research code. Not part of the SMRITI app; disabled by default (`scope.v2.enabled = false`). Simulation is not evidence of benefit for people living with dementia.**

This protocol was committed to git **before** the benchmark was run. The results file (`SCOPE_BENCHMARK_RESULTS.md`) is generated by `./gradlew :scope:runScopeBenchmark` from the code in `scope/`, using the same engine classes a future app integration would call.

## Controllers (identical inputs, identical query budget)

| ID | What it is |
|---|---|
| **B0** fixed/manual | Never learns. Always the activity's manual default variant; predicts 0.5 for every pair. |
| **B1** strong rules | Per-context (activity × Solo/Together) recency-weighted (0.9^age) variant win/loss counts, with fallback to per-activity counts; a hand-written Solo/Together table for unseen or tied variants (Solo: lower motion, shorter narration; Together: audio-supported, richer visuals); deterministic tie-breaks. Fixed probability mapping, no fitted statistical model, no generalisation from feature weights. Proposes only with a net win of ≥ 1, otherwise the manual default. |
| **B1F** rules + feature votes | B1 plus per-context, per-feature majority "direction votes" (did the chosen variant have more or less of feature f?). This is deliberately stronger than the annex's B1 because it *does* generalise heuristically through features. It was added so that SCOPE cannot win just because the rule baseline is weak. |
| **B2** non-contextual Bayesian | Same likelihood, prior and Laplace posterior as B3, but β only: no Solo/Together interaction and no activity residuals. |
| **B3** full SCOPE | β + Solo/Together × feature interaction + activity residuals with a shrinkage prior. |
| B3-nopool | B3 with cross-activity pooling turned off (activities learn independently). This is an ablation, reported but not gated. |
| B2-VOI, B3-VOI | The same models choosing their own comparisons by expected information gain (≤ 1 question per opportunity, `DoNotAsk` allowed), under the same opportunity budget. |

Frozen model settings: prior variances β 1.0, γ 0.5, δ 0.25 (no-pool δ 1.0); proposal threshold P(best ≻ runner-up) ≥ 0.70; minimum information gain 0.03 nats; top-K = 4.

## Catalogue

- **Activities:** 4 (cooking, dishes, sewing, market_stall). Each has 12 curated variants drawn without replacement from the grid visual density {0, .5, 1} × motion {0, .5, 1} × narration {0, .5, 1} × modality {visual, audio-supported}, with catalogue seed 7.
- **Split:** per activity, 8 variants form the *query pool* (the only variants ever shown in comparisons) and 4 are *unseen* (used only for held-out evaluation).
- **Manual default:** the first pool variant.

## Synthetic people

The true utility is u(a, c) = (β + s·γ + δ_activity)ᵀ x(a) + m(a), where s = +1 for Together and −1 for Solo. The answer to a comparison (a, b) is:
1. **Skip** with probability p_skip;
2. otherwise, **Both fine** with probability 0.5 if |Δu| < 0.15;
3. otherwise, **Left** with probability sigmoid(k·Δu).

| Profile | Truth | k | p_skip | Purpose |
|---|---|---|---|---|
| P1 stable-additive | β ~ N(0, 2²), γ = 0, δ = 0 | 1.0 | 0.1 | Rules may be just as good |
| P2 context-tradeoff | β ~ N(0, 1), γ ~ N(0, 2²) | 1.0 | 0.1 | Where SCOPE *should* help |
| P3 activity-specific | β ~ N(0, 1.5²), δ ~ N(0, 1.2²) | 1.0 | 0.1 | Partial cross-activity similarity |
| P4 low-feedback | as P2 | 1.0 | 0.6 | High skip rate |
| P5 noisy | as P2 | 0.35 | 0.1 | Inconsistent answers |
| P6 drift | as P2; β, γ redrawn after half the budget | 1.0 | 0.1 | Change over time (no disease interpretation) |
| P7 misspecified | as P2 + 3·s1·(mo−.5)(na−.5) + 2·s2·((vd−.5)² − 1/12), s1, s2 = ±1 | 1.0 | 0.1 | Non-additive truth |
| P8 no-context-weak | β ~ N(0, 0.8²), γ = 0 | 0.6 | 0.1 | Detect harmful overfitting |
| P9 partial-metadata | as P2; models see narration missing on 50% of variants and modality missing on 25% (fixed per variant) | 1.0 | 0.1 | Sparse features |
| P10 version-change | as P2; after half the budget the content version changes and every controller restarts (old events fail closed) | 1.0 | 0.1 | Cold start + version change |

P11 (device/viewport invariance) is covered by unit tests (`ScopeEngineTest`) rather than the simulator, because the engine has no device input at all.

**Users:**
- dev seeds 1–10 are used only to check that the code runs; nothing was tuned on them;
- the reported **held-out** users are seeds 1001–1040 (40 per profile);
- the split is by synthetic person, never by event.

**Context per query opportunity:** activity uniform over 4, mode Solo/Together 50/50, always explicitly confirmed.

**Budget:** 32 comparison opportunities per user, with checkpoints at 4, 8, 16 and 32. **The primary checkpoint is 16.** In passive mode the pair is drawn uniformly from the activity's pool by the user's seed, so every passive controller sees exactly the same event stream.

## Metrics

**Held-out** (at each checkpoint, over all 4 activities × 2 modes × all 66 pairs of the 12 variants; truth p* = sigmoid(k·Δu) using the person's *current* preferences):
- expected cross-entropy CE(p*, q) — the "held-out pairwise log loss";
- the same restricted to pairs with ≥ 1 unseen variant;
- choice agreement (q > ½ ⇔ p* > ½; q = ½ counts half);
- normalised regret of the proposal (manual default when abstaining): (u_max − u_rec)/(u_max − u_min), averaged over contexts;
- abstention rate.

**Prequential:** log loss and Brier score of P(left) on each actual left/right answer, logged *before* the update.

**Burden / stability:**
- questions asked (VOI variants may decline);
- switches, i.e. how often the proposal for a context changes after an update.

## Pre-registered go / no-go (per profile, at budget 16)

**Statistics.** Paired bootstrap over the 40 held-out users (2000 resamples, seed 99) of the relative CE improvement (CE_B1 − CE_B3)/CE_B1.

**GO vs B1** only if all three hold:
1. the relative improvement is ≥ 5% **and** the 95% CI lower bound is > 0;
2. mean normalised regret is ≥ 10% lower than B1's;
3. switches are ≤ B1's + 0.05 per update.

The same test is reported against B1F and B2.

**Verdict.** SCOPE can only be called "better than rules" if it passes against **both** B1 and B1F on P2 (the context profile) **and** does not lose significantly (CI upper bound < 0) on P1, P8 or P9.

Every failure is reported. **Whatever the outcome, SCOPE stays disabled by default.**
